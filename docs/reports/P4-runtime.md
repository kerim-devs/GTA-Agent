P4 is implemented in the four assigned runtime modules and three assigned test modules. The synchronous httpx bridge supports cropped RGB frames, status, complete controller states with 250 ms leases, and recording. The CLI exposes drive with seconds, shadow, no-record and absolute record-dir options, plus replay with an optional output path. No other source files were changed.

The live loop processes the newest available HUD frame at approximately 30 Hz. It passes monotonic receipt time minus reported frame age to the shared reader/motion/driver pipeline. Motion compares against the nearest available crop about 200 ms earlier; unknown motion stays unknown. After 300 ms without a fresh frame, the loop sends neutral once and waits. Frames already 300 ms old are also excluded from driving. HTTP 409 blocks further controller requests for one second; only a neutral request is retried, and driving resumes on a later tick after that request succeeds. Shadow never posts to the controller endpoint. Normal completion, exceptions, KeyboardInterrupt, SIGINT and SIGTERM all attempt neutral before stopping recording. Failure to neutralize does not prevent the recording-stop attempt, and cleanup failures do not replace an existing exception.

The recorder receives the absolute recording base directory and creates its own YYYYMMDD-HHMMSS child. This behavior was verified in the local remoteplay source rather than assumed from the abbreviated endpoint description. The bridge returns the daemon's actual directory, and pilot.jsonl is created there. Each tick records relative t, frame_id, frame_age in seconds, absolute monotonic frame time, every Reading field, motion, predicted command, sent and HTTP status. No-frame ticks contain null frame/reading/command fields. sent means that the logged predicted command was accepted; it remains false for a neutral recovery request even when status is 200. Summary output includes ticks, average tick rate, state counts, damaged-frame count and all 409 responses, including cleanup attempts. With no-record, neither recording endpoints nor a log file are used.

Replay uses cv2.VideoCapture, BGR-to-RGB conversion and the same pipeline. It uses frames.jsonl timestamps rather than nominal video FPS, normalizes the HUD crop to 260 by 170, and writes pilot-replay.jsonl by default. Local recorder source confirms that video indices start at zero and that frames and controller events share a monotonic origin. Replay rejects missing video frames, noncontiguous metadata indices and nonincreasing timestamps. Human steering is held until the next human event; agent events are excluded. Sign agreement includes only tilted maps with a route and human steering magnitude above 0.4. Correlation searches shifts within two seconds at the median frame interval, requires at least three eligible samples and half the unshifted sample count, and prefers the smallest absolute shift on ties. Positive shift means the human follows the pilot. Constant or insufficient data reports unavailable correlation. Notes mentioning Wi-Fi trigger the required wired-recording warning.

Validation ran from pilot/ with `.venv/bin/python tools/gate.py`. The final output was `All checks passed!`, `13 files already formatted`, `22 passed in 0.33s`, and `gate passed`. The tests use httpx.MockTransport and injected reader, motion and driver implementations. They cover the frozen-frame timeout with a 200 ms frame age, repeated 409 refusals, continued reading/logging during takeover, accepted-neutral recovery, shadow isolation, every required exit path, cleanup failure, log contents, frame-time motion, route-end braking and stale frames. The constructed MP4 replay has 16 eligible comparisons, sign agreement 7/16, and a known positive 200 ms delay; assertions verify `sign agreement=0.438 ticks=16` and `best shift=+0.200s correlation=1.000 ticks=16`. `.venv/bin/python -m pilot.cli --help` printed `usage: pilot [-h] {drive,replay} ...` and both subcommands without contacting a bridge. Scoped Ruff formatting was applied before the final gate.

The driver has no specified terminal-state name. The chosen integration assumption is therefore two seconds continuously without a route on an undamaged tilted map, motion explicitly false, and a completely neutral driver command. This avoids ending while P3 is braking and does not depend on an invented state name; integration must confirm that P3 eventually returns neutral after stopping. Other bridge assumptions are that successful frame responses contain valid RGB dimensions and nonnegative ages, 204 means no new frame, 409 rejects the whole controller update, other HTTP errors terminate the run, and successful recording startup returns an absolute directory on the same local filesystem. The loop owns the recorder while recording is enabled. A final neutral request can still be refused when the stream is down; the client attempts it and counts 409, but cannot guarantee physical controller release beyond the daemon's documented TTL.
